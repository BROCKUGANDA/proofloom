# PART II. PRODUCT VISION

## 3. What PROOFLOOM is

PROOFLOOM is a verifiable engineering and software provenance platform.

It creates an evidence-backed record of how software is developed, modified, tested, released, verified and maintained, including work performed by autonomous AI agents.

The platform connects:

- Software repositories.
- Engineering teams.
- Organizations.
- Software components and dependencies.
- CI/CD systems.
- Build and release pipelines.
- Human contributors.
- AI agents.
- Tasks and engineering activities.
- Security policies.
- Evidence artifacts.
- Cryptographic attestations.
- Public verification.
- Blockchain commitments.
- External developer tools.

Its purpose is to make engineering activity independently inspectable and verifiable.

A company should be able to establish:

- What software was released.
- Which source revision produced it.
- Which dependencies were involved.
- Which tests and security checks were performed.
- Which people and agents contributed.
- What evidence supports each claim.
- Whether the evidence has changed.
- Whether an attestation remains valid.
- Whether a release has been revoked or superseded.
- Whether another organization can independently verify the result.

PROOFLOOM should become an infrastructure layer for trustworthy software production.

## 4. Product philosophy

**The architecture of trust, made visible.**

The product should make complex engineering evidence understandable without diluting its technical rigor.

The platform must serve several distinct audiences:

- Founders and executives evaluating software trust.
- Engineering leaders overseeing releases.
- Security and compliance teams examining evidence.
- Developers integrating repositories and pipelines.
- AI-agent operators supervising autonomous work.
- Independent auditors verifying claims.
- External developers building on PROOFLOOM's protocol.

Do not create one generic dashboard for all these users. Design purposeful workspaces and information hierarchies around their actual jobs.

# PART IV. GNOLAND PROTOCOL ENGINEERING

## 15. Blockchain architecture

Gno.land is the protocol foundation for PROOFLOOM's verifiable public commitments.

The initial integration target is Onyx Testnet.

Initial network configuration:

- Network: Onyx Testnet.
- Chain ID: `onyx-1`.
- RPC: `https://rpc.onyx.testnets.gno.land:443`.
- Tooling: `gno`, `gnokey`, `gnodev`, subject to current compatibility and official documentation.
- Realm architecture: `gno.land/r/<publisher>/proofloom/` as a proposed namespace.

Verify all network configuration, tooling versions, deployment procedures and current Gno APIs against official documentation before implementation.

Do not assume that a previously documented command, package or network endpoint remains valid.

## 16. Realm architecture

Design a modular realm structure.

Suggested organization:

```text
gno.land/r/<publisher>/proofloom/
    core/
    identity/
    registry/
    releases/
    attestations/
    agents/
    policies/
    verify/
    reputation/
```

The final realm boundaries must be justified by:

- Security.
- State ownership.
- Upgrade strategy.
- Interrealm calls.
- Gas considerations.
- Public versus private data.
- Long-term maintainability.

Implement clear ownership of state and authority.

Do not expose mutable internal state through unsafe references.

Validate caller identity and authorization at every relevant boundary.

Follow Gno's actual execution and security model, including appropriate use of `cur.Previous().Address()` and interrealm authority validation where required.

Do not assume that familiar Solidity or EVM patterns translate directly to Gno.

Respect Gno realm constraints. Do not introduce unsupported operating-system access, networking, goroutines or other prohibited runtime behavior inside realms.
