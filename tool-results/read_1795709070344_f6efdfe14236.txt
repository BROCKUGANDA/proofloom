    48→    48→# PART II — PRODUCT VISION
    49→    49→
    50→    50→## 1. Product definition
    51→    51→
    52→    52→PROOFLOOM is a decentralized software provenance and AI-agent accountability platform.
    53→    53→
    54→    54→It enables organizations, developers, maintainers, auditors and autonomous agents to create, publish, inspect and verify durable records of software work.
    55→    55→
    56→    56→The platform connects:
    57→    57→
    58→    58→- Software projects.
    59→    59→- Open-source components.
    60→    60→- Development teams.
    61→    61→- Release pipelines.
    62→    62→- CI/CD processes.
    63→    63→- AI agents.
    64→    64→- Security assessments.
    65→    65→- Build artifacts.
    66→    66→- Evaluation results.
    67→    67→- Cryptographic attestations.
    68→    68→- Verifiable work histories.
    69→    69→- Third-party applications.
    70→    70→
    71→    71→The product creates a common trust infrastructure for software delivery.
    72→    72→
    73→    73→A project should be able to demonstrate:
    74→    74→
    75→    75→- Who created it.
    76→    76→- Who contributed to it.
    77→    77→- Which agents participated.
    78→    78→- What version was released.
    79→    79→- Which build produced the release.
    80→    80→- Which checks passed.
    81→    81→- Whether a security review was completed.
    82→    82→- Whether the evidence has changed.
    83→    83→- Which attestations remain valid.
    84→    84→- Whether a release or attestation has been revoked.
    85→    85→
    86→    86→PROOFLOOM must make these records independently verifiable.
    87→    87→
    88→    88→## 2. The fundamental problem
    89→    89→
    90→    90→Modern software ecosystems depend on claims that are often difficult to independently establish.
    91→    91→
    92→    92→Examples:
    93→    93→
    94→    94→- A developer says a release passed testing.
    95→    95→- An AI agent claims it completed a task.
    96→    96→- An organization publishes an audit report.
    97→    97→- A project claims that a specific commit generated a binary.
    98→    98→- A software component claims a particular security status.
    99→    99→- An organization wants to know whether an external project is trustworthy.
   100→   100→- A downstream developer needs to verify a dependency before integrating it.
   101→   101→
   102→   102→Most conventional systems distribute this information among repositories, CI/CD providers, documents, dashboards, messages and private databases.
   103→   103→
   104→   104→PROOFLOOM creates a unified verification layer.
   105→   105→
   106→   106→The application must combine off-chain execution infrastructure with durable, composable on-chain attestations.
   107→   107→
   108→   108→## 3. Product principles
   109→   109→
   110→   110→1. Evidence must be distinguishable from claims.
   111→   111→2. Every published attestation must have an identifiable issuer.
   112→   112→3. Evidence must be verifiable independently of the interface.
   113→   113→4. On-chain state must not depend on a centralized dashboard for correctness.
   114→   114→5. Private data must remain private.
   115→   115→6. AI-generated analysis must not become an unquestioned source of authority.
   116→   116→7. Agent permissions must be scoped, revocable and auditable.
   117→   117→8. A consumer application must be able to integrate the public protocol without depending on the PROOFLOOM frontend.
   118→   118→9. All important state transitions must have a traceable history.
   119→   119→10. The architecture must support future Gno.land mainnet operation.

   640→   640→## 6. Contract security rules
   641→   641→
   642→   642→Read the official Gno security documentation before implementing the realm architecture.
   643→   643→
   644→   644→Apply all applicable rules, especially:
   645→   645→
   646→   646→- Validate realm-call identity.
   647→   647→- Use `cur realm` and `cur.IsCurrent()` where appropriate.
   648→   648→- Derive caller identity from `cur.Previous().Address()` rather than trusting an address supplied as an argument.
   649→   649→- Never store ephemeral realm values in persisted state.
   650→   650→- Do not expose pointers to mutable internal structures.
   651→   651→- Return safe values or immutable-style copies.
   652→   652→- Do not invoke untrusted caller callbacks while exercising your realm's authority.
   653→   653→- Validate externally supplied interfaces and objects.
   654→   654→- Enforce explicit ownership and authorization on state-changing operations.
   655→   655→- Never confuse foreign realm read access with permission to mutate foreign state.
   656→   656→
   657→   657→Write adversarial tests against unauthorized cross-realm calls, caller impersonation, mutable pointer exposure and unauthorized administrative operations.
   658→   658→
   659→   659→Do not invent security guarantees based on the fact that Gno uses deterministic execution.
